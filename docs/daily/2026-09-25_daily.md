# Daily Development — 2026-09-25

## Zusammenfassung

Der Harness funktioniert jetzt pro Teilprojekt. In einem Repository wie
EZF-Backend kann der Core im Root ein Projekt sein, jedes Plugin ein eigenes
Teilprojekt. Die Konfiguration im Repo-Root trägt die Teilprojekte ein.
Jedes hat eigene Konfiguration, Sprache, Backlog, Tagesberichte,
Systemdoku und Architekturregeln in seinem Ordner. Die Session startet
weiter im Repo-Root.

Alle Hooks wenden die Regeln des Projekts an, zu dem eine Datei gehört. Ein
Plugin kann Architekturregeln des Core übernehmen. Tagesberichte zählen pro
Projekt nur dessen Commits, auch wenn die Session direkt im Teilprojekt
startet. `/claude-harness:init` richtet Teilprojekte ein.

Außerdem funktioniert der Worktree-Ablauf jetzt ohne Umweg. Die Hooks
bewerten Dateien im Worktree richtig.

Neu ist das Modul `semver`. Jedes Projekt hat eine einheitliche
Versionsdatei (Standard `docs/VERSION`), die in die projekteigenen Dateien
wie `package.json` oder `plugin.json` gespiegelt wird. Jede gemergte Änderung
ergibt höchstens einen Versionsschritt mit Release-Tag. Ein Hook prüft den
Schritt und die Spiegel. In Claude_Harness ist das Modul eingeschaltet, und
das erste Release `v0.1.0` ist gesetzt (nur lokal, nicht gepusht).

Ergänzt wurde der Befehl `/claude-harness:update`: ein bereits eingerichtetes
Projekt kann seine `.claude-harness/config.toml` gegen das aktuelle
Schema prüfen und auffüllen lassen, ohne Bestehendes zu überschreiben —
das Gegenstück zu `init`. Dafür löst `harness_config.py` eine Migrationskette
von der gespeicherten `version` zur aktuellen `CONFIG_VERSION` auf; die
Liste ist vorerst leer. Damit gemergt: Release `v0.2.0` (nur lokal).

## Entscheidungen und Alternativen

| Entscheidung | Grund und Alternativen | Nachweis |
|---|---|---|
| Start im Repo-Root ist der Hauptfall | Wer Plugins entwickelt, muss die Hauptanwendung lesen und gegen sie testen. Claude Code lädt Settings nur aus dem Startverzeichnis, deshalb ordnet der Harness Dateien selbst zu. | [STORY-027](../todo/items/STORY-027/) |
| Versionierung: ein Schritt pro gemergter Änderung | Teilschritte und Ausprobieren innerhalb einer Änderung werden gebündelt, direkte Commits vom nächsten Release mit erfasst. Die Versionsdatei in `docs` ist einheitlich und daher per Skript prüfbar; die Spiegel prüft eine reine Textsuche. Verworfen: Release nur auf Wunsch, Conventional Commits mit semantic-release (braucht npm), eigener Changelog (die Tagesberichte reichen), die Version in der `config.toml` (darf gitignored sein). | [STORY-029](../todo/items/STORY-029/) |
| Erstes Release `v0.1.0` | Laut Owner beginnt die Zählung mit `0.1.0`, sobald STORY-029 und EPIC-004 abgeschlossen sind; kein `0.2.0`. Tag auf `5952618`. | [STORY-029](../todo/items/STORY-029/) |
| Kein eigenes Prinzipien-Dokument | Die genannten Prinzipien (keine unnötigen Abstraktionen, keine spekulativen Features) sind natives Verhalten von Claude; projektspezifische Regeln stehen in `architecture.md`. STORY-009 ist verworfen. | [EPIC-004](../todo/items/EPIC-004/) |
| Daily-Stand nach Ordner statt Projektname | Ein Teilprojekt teilt seinen Stand, egal ob die Session im Root oder im Teilprojekt startet. Das weicht von der Spec ab und ist in den Notes festgehalten. | `9facfa9`, [STORY-027](../todo/items/STORY-027/) |
| Keine SemVer für das Config-Schema | Es gibt genau einen Konsumenten der Config (den Harness selbst); Schema und Migrationslogik werden immer zusammen ausgeliefert, additive Änderungen brauchen ohnehin keinen Versionsbump. Ein hochzählender Integer mit Migrationsliste (`MIGRATIONS`) reicht dafür aus. Verworfen: `MAJOR.MINOR.PATCH` für `version`. | [STORY-030](../todo/items/STORY-030/) |

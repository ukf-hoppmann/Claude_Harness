# Architecture rules

Binding architecture of Claude_Harness. MUST, SHOULD, and MAY have their
RFC 2119 meaning.

## Rules

### 1. Product boundary

- Everything other projects install MUST live under `plugin/`. Files outside
  `plugin/` exist only to develop the plugin and MUST NOT be required by it.
- Plugin files MUST refer to their own files through `${CLAUDE_PLUGIN_ROOT}`,
  never through paths of this repository.

### 2. Runtime

- Hook and helper scripts MUST use only the Python standard library and run on
  Python 3.11 or later. Target projects need no installation step.
  Enforced by: `tests/implementation/unit/test_architecture_rules.py` (standard library only).
- Hooks MUST NOT use the network and MUST finish within their configured
  timeout.
- Exception (approved by the project owner on 2026-11-04, STORY-052): at the start
  of a cloud session (`CLAUDE_CODE_REMOTE=true`, source `startup`) with
  `cloud.sync` on, the session start hook MAY fetch the current branch from
  `origin`. It MUST stay within a time limit below its hook timeout, MUST NOT
  fetch other refs, and MUST NOT deepen a shallow clone.

### 3. Modules

- Every module MUST check its own switch. When its module or suite part is
  off, or the configuration is invalid, a hook MUST do nothing and exit 0.
- A module MUST NOT read or change another module's documents except through
  shared helpers in `plugin/scripts/`.

### 4. Configuration

- Every configuration key MUST be validated in
  `plugin/scripts/harness_config.py`; unknown keys are errors.
- Every configuration key MUST be documented in `docs/techdocs/configuration.md`
  and covered by a test in `tests/implementation/unit/test_config.py`.
  Enforced by: `tests/implementation/unit/test_architecture_rules.py` (documentation only).

### 5. State and files

- Per-session state MUST be stored through `plugin/scripts/state.py` in
  `$CLAUDE_PLUGIN_DATA`. Hooks MUST NOT write into the project, except for
  per-clone state below `.git/claude-harness/`.
- Exception (same scope as the one in rule 2): that hook MAY fast-forward the
  current branch to `origin` when the working tree is clean. It MUST NOT
  discard, reset, rebase, or merge anything else.
- Documents in the project are written by the AI following a skill, never
  generated by a hook.

### 6. Language

- Skills, templates for AI rules, and hook messages MUST be in English.
- Documents for people (backlog, daily reports, technical docs) MUST be written
  in `docs.language`; machine-checked field names and headings stay English.

### 7. Secrets

- Code and files checked into version control MUST NOT contain literal
  secrets (credentials, API keys, tokens, connection strings with
  passwords).
- Secrets MUST be read at runtime from a project-local, git-ignored
  configuration (e.g. `.env`, `config.local.*`).
- A checked-in template file with placeholder values (e.g. `.env.example`)
  MUST exist so it is visible what can be configured; code MUST reference the
  real, git-ignored config, never the template.
- Which config a given secret belongs to MUST be clarified with the project
  owner unless an existing config already clearly covers it; the AI MUST
  point this out before writing the secret anywhere.

### 8. Paths and configuration values

- Paths, URLs, and other references to configs, databases, or services that
  can differ between environments MUST NOT be hardcoded in source code.
- They MUST be read from a config (the same config mechanism used for
  secrets, or another central, documented config).
- A path or URL that is deliberately identical in every environment MAY stay
  in code; such an exception MUST be recognizable as intentional (e.g. a
  named constant with a short comment stating why it never varies).

### 9. Load tiers

Everything that is always in context costs tokens in every session. A new
rule or piece of module behavior MUST be placed by answering these questions
in order; the first "yes" decides:

1. Can a script check it, and must it never be forgotten? → **Hook.** It
   stays silent while everything is fine; its message is short and points to
   the module's skill.
2. Does it apply only to certain folders or files? → **Architecture scope**
   with path patterns. Subfolder `CLAUDE.md` files are not used by the
   harness, because scopes cover the same purpose and their reading is
   enforced.
3. Does it apply only to one topic? → **Skill.** The description is one
   sentence saying *when* to load it and contains no rules. Details needed
   only in rare cases go into a supporting file of the skill.
4. Is it deterministic work (parsing, Git evaluation, overviews)? → **Script**
   that the skill or a hook calls, instead of describing the work in prose.
5. Does almost every task need it? → **Root `CLAUDE.md`** of the project. This
   is the exception. The plugin MUST NOT write to `CLAUDE.md`.

In addition:

- The session start hook prints one line per active module (location and
  skill); with several projects, the skill pointers appear once and each
  project gets one line with its locations. Beyond that, only short lines
  for missing files and errors.
- Skills and hooks MUST NOT duplicate each other's rule texts beyond a short
  pointer.

## Changing these rules

These rules are guidelines the project owner may deliberately break. If a
requirement or design does not fit them, the AI names the conflict and
proposes solutions, and the project owner decides (skill
`claude-harness:conflicts`). A change to this file or a scope file becomes
binding only after the project owner approves it.
